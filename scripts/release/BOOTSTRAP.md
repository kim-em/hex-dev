# Bootstrapping released repositories

`scripts/release/released.yml` is the authoritative publication graph for the
split repositories and the `leanprover/hex` aggregate. The sync workflow
clones each repository's `main`, deletes everything the entry does not allow,
overwrites its managed paths and CI workflow from this monorepo, copies the
release toolchain, generates the Lake file (see `PLAN/Releases.md` §The
generated Lake file), rewrites the lockfile to the release, and pushes the
result. It does not create repositories.

A released repository carries the library and nothing else: Lean source, the
umbrella module, its SPEC and its README. Benchmarks, conformance drivers,
fixtures and oracles are development instruments for the whole graph, so they
live in this monorepo and run in its CI; each mirror's workflow builds what it
publishes.

That is enforced by construction, not by remembering. `allowed_paths` in
`sync_released.py` computes what a mirror may hold — the entry's managed paths
plus the skeleton below — and `prune_unmanaged` deletes everything else, so a
newly admitted entry inherits the policy with no cleanup list of its own. The
`pins_only` aggregate is exempt from the sweep: it manages no source, and its
umbrella module, lakefile, `docs/` site and the workflow that publishes it live
only in the released repository, where nothing here could tell them from an
accident. It still loses `.claude/`, which no released repository has any use
for and which is therefore deleted by name from every entry.

The skeleton the sweep keeps is the generated `lakefile.toml` or `lakefile.lean`,
`lake-manifest.json`, `lean-toolchain`, `LICENSE`, `.gitignore`, `AGENTS.md`
and `README.md`. Under `.github/` only the workflows `released-ci.yml` declares
for that repository survive: every mirror has `workflows/ci.yml`, and an entry
under `extra_workflows:` adds one more by name, so a mirror cannot accumulate a
workflow nobody here publishes. The `pins_only` aggregate is the only
repository with an extra, its `docs` renderer. A
mirror carries no `reports/` tree and no `.claude/` notes: bench results,
performance write-ups and agent orientation belong to the whole graph and stay
here. The one exception is a figure a manifest entry names in its `figures:`
list, which arrives as a managed file under `reports/figures/`.

A mirror-local file outside all of that — `hex-test-kit`'s fixed
`HexTestKit.lean` umbrella is the only one — needs a `keep_paths` entry in the
manifest. That escape hatch can only preserve, so forgetting it shows up as a
deletion in the dry run rather than as an over-published mirror.

The manifest is checked locally by:

```sh
python3 scripts/release/check_released_manifest.py
```

That check is network-free. It verifies source paths, unique destinations,
topological ordering, aggregate coverage, the standalone regression-test
module lists, and that every `pins` list is exactly the published part of the
library's transitive dependency closure.

## Repository set added for factorization and roots

The factorization and roots publication adds these repositories, in dependency
order (the manifest remains the source of truth for the exact order):

- foundations: `hex-arith`, `hex-poly`, `hex-mod-arith`, `hex-poly-theory`,
  `hex-poly-fp`, `hex-poly-z`, `hex-mod-arith-theory`, `hex-gfq-ring`;
- lifting and root bounds: `hex-hensel`, `hex-poly-z-theory`,
  `hex-hensel-theory`, `hex-roots`, `hex-real-roots`, `hex-roots-theory`,
  `hex-real-roots-theory`;
- factorization: `hex-berlekamp`, `hex-berlekamp-theory`,
  `hex-berlekamp-zassenhaus`, and `hex-berlekamp-zassenhaus-theory`.

Computational repositories remain Mathlib-free. Repositories ending in
`-theory` depend on Mathlib and contain the correspondence proofs and
Mathlib-facing APIs.

## Repository set added for multivariate polynomials

The multivariate-polynomial publication adds:

- `hex-mv-poly`, the Mathlib-free computational library, after `hex-basic`
  and `hex-poly`; and
- `hex-mv-poly-theory`, the theory companion, after `hex-mv-poly` and
  `hex-poly-theory`.

The core repository ships its library and its regression-test modules; its
benchmark, SymPy conformance oracle, fixtures and kernel proof probes stay
here, as does the bridge's Mathlib-correspondence conformance target.

## Starting files

Create each repository under `leanprover`. The initial `main` must contain:

- `lean-toolchain` in the root; its initial contents are copied from this
  monorepo and subsequent release upgrades are sync-managed;
- `lake-manifest.json` generated by Lake, not assembled by hand: write a
  temporary lakefile requiring the library's direct dependencies (for
  example the Lake file `render_lakefile` prints for the entry), run
  `lake update`, and commit both; the first sync replaces the lakefile and
  stops before pushing if the lockfile lacks a package it requires;
- `LICENSE`, `AGENTS.md`, and `.gitignore`.

Everything else arrives with the first sync: the source, umbrella module,
README and SPEC; the repository's workflow from
`scripts/release/released-ci.yml`; and the Lake file, generated from the
manifest entry and this monorepo's `lakefile.lean`. Describe the library's
build there, not in the mirror: its `lean_lib` settings, its `test_modules`,
`build_modules` and `executables`, and, under `lake_declarations`, any native
targets or carrier libraries it needs (`PLAN/Conventions.md` explains the
carrier pattern for C code). The sync also validates that every `scripts/ci`
helper named by the managed workflow exists in the mirror, and stops before
changing that repository if one is missing.

Do not duplicate or hand-edit any managed file in a released mirror. Add a new
repository's complete workflow to `scripts/release/released-ci.yml`; the
manifest checker rejects missing and extra workflow entries, rejects an entry
that asks to publish benchmarks, conformance drivers, fixtures or oracles,
rejects a `keep_paths` entry naming any tree no mirror publishes, and renders
every entry's Lake file.

`require`s list direct dependencies only; Lake resolves the rest transitively.
The longer `pins` list in `released.yml` is deliberate: the sync rewrites the
entire published transitive closure in the lockfile.
Non-Hex dependencies are likewise resolved from this monorepo's exact
`lake-manifest.json`, so a stable toolchain release cannot leave older Mathlib
commits in an existing mirror.

## Baseline and first publish

Do not add placeholder entries to `scripts/release/synced.json`. An absent
baseline is how the first publish is distinguished; any truthy, incorrect SHA
causes the uncoordinated-commit guard to skip the repository.

After every repository exists with its starting files, ensure the fine-grained tokens behind
`RELEASED_SYNC_PAT` and
`RELEASED_SYNC_PAT_2` select every target repository and grant both
`Contents: Read and write` and `Workflows: Read and write`; the latter is
required because the sync publishes `.github/workflows/ci.yml`. Then:

1. Run the local manifest check and the complete monorepo build.
2. Dispatch `.github/workflows/sync-released.yml` with `dry_run=true`.
3. Inspect every managed-path copy, scheduled deletion and pin rewrite, and
   confirm there are no missing-source warnings or uncoordinated-commit skips.
4. Dispatch again with `dry_run=false` only after the dry run is clean.
5. Watch each mirror's own CI on the sync push; a build-only workflow on the
   published tree is what establishes that the mirror is coherent.

Some libraries used `v0.1.0` before releases were coordinated, so the first
shared release is `v0.2.0` across every released repository.
Each later complete release increments the shared minor version and resets its
patch component to zero. Lake files use that tag as their cross-Hex input
revision; manifests record both the tag and its exact resolved commit.

The real workflow advances the `release-sync-baseline` branch in the same run.
It records a pending version before the first push and each repository as its
tag is published. If a later mirror fails, rerun the workflow at the same
hex-dev commit: it resumes that version, and only marks the release complete
after every mirror carries the tag. Completed mirrors retain their recorded
commits and pins on every resumed run.

For a release that needs a Mathlib update between phases:

1. Set `only` to the computational repository short names and any companions
   that can already build. Use spaces or commas, and include each selected
   library's unpublished dependencies. Run with `dry_run=true`, then
   `dry_run=false` after checking the preview and consumers. This leaves the
   shared version pending.
2. Get Mathlib's Hex pins updated, then update the Mathlib requirement and
   compatibility proofs in hex-dev. Keep already-published sources, toolchains
   and build settings unchanged; use a release branch if necessary.
3. Run the dry and real workflows at that new source with
   `advance_source=true`. Leave `only` empty to publish all remaining
   repositories, including the aggregate last, or select another intermediate
   phase. The pending version is reused.

The driver verifies every completed mirror's source fingerprint and immutable
tag before publishing at a newer source commit. `--force` does not bypass those
checks. A legacy pending release without fingerprints can only retry at its
original commit. Every phase stages its actual dependency closure and requires
consumer checks; the publishing job also rejects a baseline or selection that
differs from the consumer-checked plan. See
[Staged publication](../../PLAN/Releases.md#staged-publication) for the rules.
Mathlib-dependent phases require Mathlib's own Hex dependencies to match already
published commits at this version. The staged consumers verify every resolved
Mathlib dependency before cache retrieval. Earlier companions keep their original
Mathlib pins; later phases test their compatibility with the current pins.
The manifest's repository list cannot change while a release is pending.

After a partial publication or failure, dispatch the entire workflow again.
Do not use Actions' "Re-run failed jobs" on the publishing job: its old staged
plan predates the advanced baseline, so the plan check will reject it. A new
dispatch stages the remaining repositories against the current baseline.

If a runner is lost after a push and before the baseline is published, retain
the run's `release-stage` artifact. Restore its plan's `baseline` to
`release-sync-baseline:synced.json`, preserving any prior pending progress, and
add or update `_pending_release` with the plan's `version` and full `source`.
For a newly allocated release, start its `repos`, `fingerprints` and `sources`
empty. Dispatch at that exact source commit, first dry and then real. Recovery
checks each unrecorded tag's parent against the restored baseline, its sync
commit message against the source, and its contents against the regenerated
tree. Do not advance the source until that recovery finishes, and never delete
or move the existing tags. If the artifact or original source cannot be
recovered, reconcile the recorded and published commits before proceeding.

Future out-of-band changes to a released `main` must be re-seeded into this
monorepo before publication continues; never bypass that reconciliation with
`--force` merely to make a release proceed.
