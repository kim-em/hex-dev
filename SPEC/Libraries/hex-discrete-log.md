# hex-discrete-log

Certified discrete logarithms in finite-field multiplicative subgroups.
Given a nonzero base `g` of proved exact order `N` and a target `h`, compute
the unique `x < N` satisfying `g^x = h`, or prove that none exists. Provide
Shanks baby-step giant-step, Pohlig-Hellman, and bounded Pollard rho, with
separate contracts for complete decisions and incomplete searches.

## Scope and dependencies

`HexDiscreteLog` is Mathlib-free and depends on `HexBasic`, `HexGFq`,
`HexIntFactor` and `HexModular`. Its namespace is `Hex.DiscreteLog`.
`HexDiscreteLogMathlib` depends on this library, `HexGFqMathlib` and
`HexIntFactorMathlib`, plus Mathlib. No permutation-group, elliptic-curve,
sparse-matrix or external CAS dependency is introduced.

The first public adapters are the nonzero elements of canonical `GFq` and
packed `GF2q`. Keep the algorithm modules independent of the representation
behind a small lawful commutative-group interface: executable equality,
identity, multiplication, inversion and natural powers, with the group laws,
sound equality, and agreement of powers with repeated multiplication. The
ambient group need not be cyclic; only the subgroup generated by `g` is.
No enumeration of the ambient group belongs in this interface.

An ordered-key interface is additionally required by the deterministic baby
table: comparison is a total order whose equality is exactly group equality.
For finite fields use canonical reduced coefficient vectors (fixed degree,
zero padded), or the canonical packed representation, with proved injectivity.
Do not compare unreduced polynomial presentations or accept a hash collision
as equality. The minimal group interface supports the proofs now; future
elliptic-curve adapters can reuse it without making an elliptic-curve library
a prerequisite of this implementation.

Index calculus, relation collection, cryptographic parameter generation and
security estimates are outside this library. Index calculus remains a
separate planned consumer of sparse linear algebra. There is no promise of
solving arbitrary large discrete logarithms within a supplied budget.

## Exact order and field adapters

A checked problem packages `g`, `N > 0`, and a proof that `N` is its least
positive identity exponent. Prove the reusable periodicity equivalence

```text
g^a = g^b  iff  a % N = b % N.
```

Define `InSubgroup g h := ∃ x : Nat, g^x = h`, without Mathlib, and prove
that every such target has exactly one exponent in `[0,N)`. The exact order
is the order of the selected base, not automatically the size of the field's
multiplicative group. Arbitrary nonzero bases, including proper-subgroup
generators and the identity, are supported.

`checkOrder g N F` takes `F : CheckedFactorization N` and checks
`g^N = 1` and `g^(N/q) != 1` for every distinct prime `q` in `F`.
Prove that acceptance gives exact order `N`. The positive subject and complete
prime support are provided by the checked factorization. Missing prime
factors, an incorrect subject, and duplicate or composite raw prime entries
must fail the corresponding decode/check stage. For `N=1` the prime list is
empty and acceptance is exactly `g=1`.

`Hex.Nat.OrderCert` in `HexIntFactor/Order.lean` and its correctness theorem concern
natural residues modulo an integer; they are not already a generic
finite-field order certificate. Generalize the needed proof in the lawful
group setting here, reusing factorization support and exponent-divisibility
lemmas where applicable. Keep the existing modular API compatible.

A second constructor accepts an existing proof of exact order directly;
BSGS and rho do not require factorization of `N`. For a Conway generator,
reuse the committed primitivity evidence and its order proof through the
appropriate computational/Mathlib boundary. A field cardinality equation
alone must not assert that an arbitrary base is primitive.

As an explicit convenience, `orderFromMultiple g M F hM`, given positive
`M`, a complete factorization `F` and `hM : g^M = 1`, repeatedly removes
prime factors `q` while `q` divides `current` and `g^(current/q)=1`.
Return the resulting exact order
and its checked factorization, proving the reduction loop and terminal
minimality. For a supplied prime-power exponent `e`, this uses at most
`e+1` power tests for that prime, not enumeration of all exponents.
Factoring `M` is a separate bounded task;
its exhaustion cannot be presented as an exact order or hidden inside BSGS.

Typed field adapters use the subtype of nonzero elements. Raw entry points
reject base zero as invalid; for a valid nonzero base, target zero has a
proved absent logarithm. `GF(2)` and base one have order one: the only
successful exponent is zero at target one. Preserve the explicit field
presentation and degree in caches, fixtures and prepared problems.

An upper bound or an unfactored multiple of the order is not an exact-order
problem. Interval searches with weaker input contracts may be added later;
these APIs must not silently accept such inputs and promise canonicality.

## Results and resource limits

Use three distinct mathematical outcomes:

| Result | Meaning |
| --- | --- |
| `found x` | `x < N` and `g^x = h`, hence the unique canonical exponent. |
| `absent` | No exponent gives the target. Requires a complete argument. |
| `exhausted reason` | The chosen computation stopped without deciding the problem. |

Invalid input is a separate decode/validation error. Exhaustion includes
operation budget, table capacity, walk/restart limit and replay capacity.
No zero exponent or empty table serves as a failure sentinel. An internal
checker rejection must remain an explicit implementation error, not absence.

The total mathematical BSGS algorithm terminates on finite loop bounds and
returns a complete decision. User-facing `...With` algorithms additionally
check memory and operation limits before allocation and while working.
Budgets count group operations, table comparisons, walk steps, collision
candidates and certificate work; report the units, and charge child calls
against the remaining parent budget. Nested prime-power solves must not
reset the whole budget. Runtime cancellation yields exhaustion.

Provide explicit `bsgs`, `pohligHellman` and `rhoWith` routes, and prepared
BSGS/PH plans for repeated targets. A convenience dispatcher may select from
these using the supplied order/factorization and resource limits, but records
its route and does not launch an unbounded fallback after exhaustion.
Prepared plans depend on the group representation, base, exact order and
parameters; neither cached target results nor a plan for another base may
be reused without validated identification.

The intended public operations are:

| Operation | Contract |
| --- | --- |
| `checkOrder`, `orderFromMultiple` | Establish the exact base order from the checked inputs described above. |
| `prepareBsgs problem b` | Build a complete baby table and giant-step multiplier, with `1 <= b <= N`. |
| `bsgs plan h` | Complete canonical-log decision using the prepared table. |
| `preparePH problem F` | Check factorization alignment and prepare the prime-order digit tables. |
| `pohligHellman plan h` | Complete digit-lifting decision with deterministic BSGS digits. |
| `rhoWith problem h seed limits` | Reproducible bounded walk, retaining advanced random state and work counters. |
| `checkLog problem h x` | Check a bounded exponent witness, independent of how it was found. |

Provide bounded construction/query forms for both prepared algorithms.
An unsuccessful preparation returns no usable complete plan. Rho digit
solving is an explicit PH option with bounded-result semantics; it must
not change the complete default's theorem.

## Baby-step giant-step

For `1 <= b <= N`, prepare the baby table `(g^j,j)` for `0 <= j < b`
using successive multiplication. Sort by the lawful group key, retaining
its exponent, and prove that every baby power occurs exactly once. Exact
order implies distinctness within this range. A future hash-table route
needs its own invariants and complexity accounting; the first route is a
sorted array with binary search.

Let `a = ceil(N/b)` and `c = g^(-b)`. At giant step `i`, starting with
`h`, look up `h*c^i`. A match at baby exponent `j` gives `x=i*b+j`.
Accept only if `x<N` and the final equality `g^x=h` checks. Iterate
`i=0,...,a-1`; the final partial rectangle is clipped by the `x<N` test.
The target sequence is updated by multiplying by the precomputed `c`.

Prove `bsgs_spec` from the division decomposition `x=(x/b)*b+x%b`:
found exponents satisfy the equation and bound, and complete traversal
returns absent exactly when `InSubgroup g h` is false. This proof covers
nonmembers without assuming the ambient group is generated by `g`.
For the default plan choose `b=ceil(sqrt(N))` by exact integer square root,
clamped to `[1,N]`; order one is handled directly. A smaller positive `b`
implements an explicit time/memory tradeoff. Zero capacity does not become
`b=1` silently.

The table-construction certificate checks the full sequence beginning at
one, its recurrence, exponent indices and sorted lookup representation.
A negative certificate additionally accounts for every giant step, its
recurrence and the lack of a valid match. A producer-supplied incomplete
baby table must never prove absence. Replay can reconstruct the sequences
from `g,h,N,b` instead of storing them, but must charge the full work.
Positive answers need only the exponent and final power check.

## Pohlig-Hellman

Require a complete `CheckedFactorization N`, with distinct prime powers
`q^e`. The exact order and factorization are prepared once and retained.
For each factor, recover the residue `x mod q^e` by successive digits.
Set `gamma=g^(N/q)`; prove that it has exact order `q`, and prepare one
baby table for this base to reuse across all `e` digits and target queries.

Starting with `x_0=0`, for `j=0,...,e-1` compute

```text
u_j = (h * g^(-x_j))^(N / q^(j+1))
d_j = log_gamma(u_j),  0 <= d_j < q
x_(j+1) = x_j + d_j*q^j.
```

The induction says that if `h=g^x`, then `x_j` is `x mod q^j` and the
next displayed equation has exactly the needed digit solution. All divisions
are exact by the certified prime-power decomposition. This is digit lifting,
not BSGS on a subgroup of order `q^e`.

The deterministic default solves digits by complete BSGS. A caller may
explicitly choose bounded rho for large prime digits; a digit-search
exhaustion propagates to the whole result. A complete absent digit proves
the original target is outside `<g>`. If every digit succeeds, combine the
residues using `HexModular` CRT, prove that the final modulus is `N`, and
normalize any symmetric CRT representative to `[0,N)` before converting to
`Nat`. Finally check `g^x=h`. If it fails, the complete digit derivation
and CRT uniqueness prove absence, not merely a guessed failure.

That final check matters for general ambient groups: `h^N=1` alone does
not prove `h∈<g>`. Even in cyclic finite-field groups, it must not replace
the exact-base-order contract. For `N=1`, bypass the empty CRT combination
and decide whether `h=1`.

Prove `pohligHellman_spec`, giving the same complete decision as BSGS for
the deterministic digit solver. A certificate for a negative PH result
contains the failed complete digit decision and preceding digit equations,
or all successful digit equations, CRT reconstruction and the final mismatch.
The checker derives the corresponding necessary congruences before claiming
absence. Successful logarithm certificates remain the small exponent witness.

Partial factorization does not enter this complete PH API. A future hybrid
may return certified congruences and a residual search problem, but such
progress is neither a unique full logarithm nor a proof of nonmembership.

## Pollard rho

Use an explicitly seeded, reproducible walk with Brent cycle detection.
Store a state `(X,a,b)` satisfying `X=g^a*h^b`, with `a,b` reduced modulo
`N`. First check `h^N=1`; if it fails, the equation gives a sound immediate
nonmembership witness. If it passes, reducing the `h` exponent modulo `N`
is valid, even when membership is not yet known.

A deterministic partition of canonical element encodings selects one of
three updates: multiply by `g` and increment `a`; multiply by `h` and
increment `b`; or square `X` and double both exponents. Seeded restarts
select initial exponents and partition parameters, recording them for replay.
Prove the state invariant for every update and restart; partition quality
is a performance question, not a correctness hypothesis. The same element
must select the same update within a walk. A constant/pathological partition
may exhaust the budget but cannot produce a false logarithm.

At a collision `g^a*h^b = g^a'*h^b'`, every logarithm satisfies

```text
B*x = A (mod N),  B = b-b',  A = a'-a.
```

Normalize signed differences before natural modular arithmetic. Compute
`d=gcd(B,N)`. If `d` divides `A`, solve the reduced coprime congruence
modulo `N/d` using extended gcd, giving candidates
`x=x_0+k*(N/d)` for `0 <= k < d`. Check each tested candidate in `[0,N)`
by exponentiation against the original target. A noninvertible `B` is not
permission to divide modulo `N`; the `d`-candidate case is required even
when the intended fast path usually uses prime-order subgroups.

Unhelpful collisions (including `A=B=0`), an insoluble congruence, or a
candidate count exceeding the remaining budget may trigger a bounded
restart. Charge candidate power checks and restarts separately from walk
steps. Apart from the initial `h^N != 1` refutation, the first rho API
returns only a checked found exponent or exhaustion; failure to find a
useful collision does not prove absence. When candidates are tested only
partially, exhaustion must not be relabelled nonmembership.

No theorem promises success for a fixed seed or budget. The usual square-root
collision heuristic is conditional on a suitable random-walk model; this
specific deterministic partition is not proved to be a random map. Benchmarks
report all preregistered seeds, successes, exhaustion and actual steps. Do not
condition timing statistics on successful runs without showing the rest.
Distributed distinguished-point walks and parallel collision tables are
later work.

## Certificates and Mathlib correspondence

`checkLog g N h x` checks `x<N` and `g^x=h`. With the exact-order proof,
`checkLog_sound` gives canonicality and uniqueness. It does not need to
replay the algorithm that found `x`. Its kernel replay requires an exposed
structural power checker, or a checked multiplication chain whose operations
agree with the executable field arithmetic. Do not assume compiled
well-founded powering reduces cheaply in the kernel.

Negative decisions use complete BSGS/PH certificates as above, or the simple
`h^N != 1` obstruction. Expose their Boolean checkers and prove soundness.
The raw certificate envelope records the field presentation, base, target,
order, route and schema version, with explicit byte/node/table limits.
Validate every raw reference and canonical element encoding. A cached
certificate is untrusted data and is replayed. Large negative certificates
may be much more expensive than positive witnesses; no compactness promise
is made. Never use `native_decide`, a new axiom, or an external CAS verdict
as a proof.

The companion identifies the computational nonzero-field group with the
units of the corresponding Mathlib field using the existing `GFq` and
packed-to-generic correspondence. Its headline `log_spec` states that a
complete solver returns `x` exactly when `x<N` and the converted equation
`g^x=h` holds, and absence exactly when the target is outside
`Subgroup.zpowers g`. Connect the stored exact order to `orderOf g`.
Bounded-result theorems preserve exhaustion without asserting nonmembership.

Transport exact-order checks/reduction, canonical uniqueness, BSGS coverage,
prime-power digit equations, CRT assembly and rho witness correctness.
Use one coherent set of executable and Mathlib group operations; do not
introduce a second incompatible power instance. The computational interface
also admits a small noncyclic test group for detecting false subgroup tests.

`HexDiscreteLogMathlib` is correspondence-only. Mark it
`correspondence_only: true`, with absence class **correspondence-only-layer**,
and put build-only examples in `HexDiscreteLogMathlib/Tests.lean`.

Computational conformance owner: `HexDiscreteLog`.

Computational performance owner: `HexDiscreteLog`.

A specialized discrete-log tactic is outside the first scope. Kernel replay
examples exercise literal certificate checks and the correspondence theorem.
Runtime search, reification and replay remain separately measured core work.

## Complexity and benchmark contracts

Write `a=ceil(N/b)`, and charge a group multiplication, inverse, comparison,
encoding and power separately from integer arithmetic. With the sorted baby
table, preparation costs `O(b)` group multiplications and `O(b log(b+1))`
comparisons; a target query costs `O(log N+a)` group operations and
`O(a log(b+1))` comparisons, using `O(b)` stored elements. Encoding and
comparison cost depends on field degree and coefficient width. Do not call
this hash-table complexity or suppress the sorting/search factors.

For PH with `N=product q^e`, prepared digit bases/tables and baby width `b_q`,
the group-operation cost per target is
`O(sum_(q^e) e*(log N + ceil(q/b_q)))`, plus the corresponding binary-search
comparisons, table preparation and exact CRT work. Memory can reuse the
largest digit table when processing factors sequentially; a prepared plan
retaining all tables records their sum. Counts do not include factoring `N`
or proving its exactness: report those explicitly as setup costs.

Rho with Brent detection retains a constant number of group elements and
`O(log N)`-bit exponents, aside from the supplied problem/certificates.
Report the actual bounded work. A `sqrt(N)` success-time claim is heuristic
unless the required walk assumptions have been justified; correctness of
returned exponents supplies no such runtime theorem.

Create `bench/HexDiscreteLog/Bench.lean` with these families:

| Family | Required variation |
| --- | --- |
| `bsgs-order` | Exact subgroup order, member and nonmember targets, full and clipped final rectangles. |
| `bsgs-memory` | Baby width at fixed order, exposing preparation and giant-step tradeoffs. |
| `repeated-targets` | Fresh setup versus prepared queries with the same base and varied target count. |
| `field-representation` | Field degree and coefficient width; packed versus generic binary arithmetic on matching fields. |
| `prime-power-digits` | Prime digit order and lifting exponent varied separately, with table reuse visible. |
| `smooth-orders` | Complete order factorization shape and largest prime factor, PH versus BSGS. |
| `rho-walks` | Prime/composite orders, fixed seed schedules, collision usefulness, retries and exhaustion. |
| `order-certification` | Exact-order checks and reduction from multiples, with stored factorization. |
| `certificate-replay` | Positive powers, complete negative BSGS/PH, encoding and kernel replay sizes. |

Follow the ordered evidence modes of [benchmarking](../benchmarking.md).
A subgroup-order ladder in finite fields often changes the cost of group
arithmetic too; report and account for both effects rather than fitting a
square-root wall-time curve. Rho's deterministic step kernel can have a
step-count model independently of its end-to-end success distribution.
Report failure rates and resource caps along with any successful timings.
A fixed operation budget requires the existing policy's justification.
Profiles include table allocation/sorting, comparisons, field arithmetic,
digit powering, CRT, walk updates, collision solving and replay.

## Conformance and external comparisons

Create `conformance/HexDiscreteLog/{Conformance,EmitFixtures}.lean`,
`conformance-fixtures/HexDiscreteLog/discrete-log.jsonl`, and
`scripts/oracle/discrete_log_pari.py`. The small-field reference enumerates
successive powers directly and never implements BSGS, PH or rho. It checks
all targets for a selection of bases, including proper-subgroup bases.
Its finite-field arithmetic is independent of Hex's executable operations.

The required external oracle is PARI/GP, using `fflog` on explicitly supplied
finite-field presentations and `znlog` on the prime-field subset. Supply the
exact base order (and its factorization where accepted). Match the actual
modulus and coefficient embedding: two isomorphic fields with arbitrary
unrelated generators are not interchangeable test inputs. For successful
queries compare canonical exponents and independently verify the equation.
For targets outside the base subgroup, use the exhaustive small reference
or an independently justified subgroup criterion before invoking an oracle
whose input domain presupposes membership.

PARI's native `fflog`/`znlog` portfolio is an **informational** throughput
comparator: it may use generic methods or index calculus and does not emit
Lean certificates. Use a persistent process, record versions/options and
chosen methods where observable, and separate setup from repeated queries.
Do not label a native PARI portfolio timing as an isolated BSGS or rho timing
without an API that actually selects that algorithm. Cross-check BSGS and
complete PH internally on every shared fixture. Certificate replay has
**no-comparable-surface-in-named-comparator** and needs native and kernel
evidence owned by the core. Failure and zero-field-input checks remain
functional cases even where the external API has no matching result type.

Fixtures include canonical field modulus/degree, base, target, exact order
and certificate, complete factorization when used, baby width, route,
seed/budgets, outcome and exponent. Cover:

- Orders one and two, zero raw base/target, identity targets, nonprimitive
  bases, and nonmembers passing an ambient exponent test in a noncyclic group.
- Every `b` for small orders, square/nonsquare orders, last-step matches,
  and insufficient table/step budgets.
- Prime powers with several lifted digits, several distinct prime factors,
  incomplete/incorrect factorizations, symmetric CRT residues and order one.
- Rho collisions with invertible and noninvertible coefficients, insoluble
  congruences, `A=B=0`, early cycles, candidate-cap exhaustion and bad partitions.
- Correct exponents near `N-1`, wrong exponents, mismatched field/order/base
  in a cached plan, missing baby entries and omitted giant-step coverage.
- Order reduction where the initial multiple is strictly larger than the
  base order, and factors requiring repeated removal.

Extend the existing oracle/CI scripts and single job. Benches and core replay
probes remain Mathlib-free; the companion's examples are build-only.

## Implementation order and manual

1. `Group.lean`, `Order.lean`, `Field.lean`: lawful operations/keys, exact
   order and its checker/reduction, finite-field adapters and edge cases.
2. `Bsgs.lean`: sorted prepared tables, complete traversal, budgets and proofs.
3. `PohligHellman.lean`: repeated prime-order solves, digit lifting and CRT.
4. `Rho.lean`: seeded walks, Brent detection and complete collision arithmetic.
5. `Certificate.lean` and `API.lean`: raw checks, public route selection,
   resource accounting and prepared-plan interfaces. Develop their soundness
   alongside each algorithm rather than postponing all verification.
6. Companion correspondence, conformance, benchmark families, replay probes
   and `HexManual/Chapters/HexDiscreteLog.lean` complete the public surfaces.

The manual first solves a small finite-field logarithm with a checked order
and demonstrates a target outside a proper subgroup. Then compare PH and
BSGS on a deliberately smooth order and a prime-order subgroup, showing
prepared-table reuse. A bounded rho example reports both a checked answer
and exhaustion under a smaller budget. Include a recurrence-stream shift
example when its sequence library is available. Examples use explicit small
mathematical inputs; they make no security claim about production parameters.

Both libraries begin planned at phase zero. Activate through normal phase
checks; the existing IntFactor performance-certification issue does not
become resolved merely because this dependent SPEC is written. Publish
through the monorepo's guarded release mechanism when the pair is ready.

Algorithm references: Shanks baby-step giant-step, Pohlig-Hellman and Pollard
rho are described in the [Handbook of Applied Cryptography, chapter 3](https://cacr.uwaterloo.ca/hac/about/chap3.pdf).
Oracle API contracts are in the [PARI arithmetic and finite-field reference](https://pari.math.u-bordeaux.fr/dochtml/html-stable/Arithmetic_functions.html).
