## Findings, most important first

1. **Unbounded raw degree growth is a design risk the experiment hides.** Nonzero representatives are never reduced (`Algebraic.lean:48`, `:64`), so every multiplication adds degrees, and every later zero test divides a larger polynomial. The zero test already computes the remainder at `Algebraic.lean:38`, so storing it when nonzero is free. The descriptors here are monic, and `SPEC/Libraries/hex-real-closure.md:144` permits reduction by a monic defining polynomial. Decide this before step 2, since it changes the storage invariant the proofs are about.

2. **The batching recommendation is drawn from the easy case.** Batching is legitimate reuse for ring operations, and its equivalence proof is routine. It does not extend to division: the elimination loop must decide the leading coefficient's zero status at every step (`DivGcd.lean:104`, `:264`), and Sturm sequences are division-shaped. It also does not compose through towers: level-two raw arithmetic still packs at level one on every coefficient operation (`Nested.lean:19`). Finally, the baseline is an unoptimized zero test: every generic pack runs a gcd (`results/checks.jsonl:66`), which a known-irreducible fast path or a stored remainder would remove. Add a `divMod`/`gcd` arm over `DensePoly (Element d)` and a cheaper-zero-test arm before committing.

3. **The "cancellation-heavy product" check does not test what it claims.** With p = [a, a] and q = [a, −a] (`Check.lean:65`), the inner coefficient is −X² + X², which is structurally zero in Q[X]; no Sturm-detected zero occurs. Use p = [X, 1] and q = [−2, X], whose inner coefficient is the raw nonzero X² − 2. The important case, a Sturm-detected leading-coefficient cancellation, is exercised by the division records, and the report should say that rather than pointing at this check.

4. **Validity is a hypothesis of everything and is carried nowhere.** Zero-test soundness, the Bézout identity in `invert`, and `refine` all need `valid d`. The report acknowledges this, but step 2 should state every theorem with `valid d = true` and the production API should make invalid descriptors unconstructible.

5. **Sign determination is missing and step 3 misdescribes its starting point.** `signSqrt2` is hard-coded to one quadratic field. Step 3 says "generalize the one existing Tarski primitive", but `ZPoly.tarskiQuery` exists only in `HexRealRoots/SPEC/hex-real-roots.md:135`; no Lean declaration exists. Sign is part of the execution contract (`SPEC/real-closure-execution.md:74`) and is on the critical path for any depth-two zero test. A general sign over rational-algebraic descriptors can be built from the existing `sturmCount` by interval refinement without a Tarski query. Consider including it in step 2 so the vertical slice is actually complete.

6. **Instrumentation validation is overstated.** Matching outputs show the shadow computes the same product, not that its counts equal the kernel's. The counts are right by inspection of `HexPoly/Operations.lean:543`, and `verify.py:102` checks the shadow's formula against itself. Reword the report accordingly.

7. **Oracle gaps.** Split minimality is unchecked (`verify.py:89`): an implementation that always split down to X² − 2 would pass. Add an exact check that the discarded factor is the monic gcd of the operand with the defining polynomial. The sign oracle at `verify.py:69` reimplements the same formula, so it is a duplicate rather than an independent check.

8. **Context splitting.** Inverses are packed back into the unsplit descriptor (`Algebraic.lean:81`), so downstream zero tests fall onto the gcd plus Sturm path; the shared-factor arms measure that penalty at one level, and at level two every coefficient operation pays it. `Element d` is indexed by descriptor values, so a runtime split changes the type of every live value at every level; the experiment's transport is one level and unrestricted (`Algebraic.lean:86`). This is fine for proofs but the runtime API must follow the SPEC's opaque-context design.

9. **Timing presentation.** The "Each op" column is the time of one whole polynomial product. Each block contributes one auto-tuned sample per arm, six per arm overall, and the digest is common to both arms, so ratios are conservative. This is adequate for an informational comparison and the report already refuses extrapolation.

## Plan scoping

Step 1 is appropriate. Step 2 is too large as one unit. Split it into zero-test plus arithmetic preservation, then inversion, splitting and transport, then transfer instantiation plus xgcd, each closable on its own. State the semantic target: the real numbers via `sturmCount_eq_card_roots` (`HexRealRootsMathlib/ChainCorrespond.lean:1392`, which needs positive degree and rational squarefreeness, so the companion needs "a divisor of a squarefree polynomial is squarefree" and the primitive-part root lemma) is available now, while an abstract real closed field waits on hex-sturm-mathlib. `Transfer.lean` is Mathlib-free and generic and can be promoted to `HexPoly` as is. Settle finding 1 before any of this, since it determines the invariant.
