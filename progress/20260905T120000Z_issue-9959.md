# Issue #9959: automorphism generators for hex-graph-iso

2026-09-05, feature session.

## What landed

`Hex.GraphIso.autos` is the new public surface: the automorphism
generators the pinned nauty traversal discovers, in discovery order,
with the vertex orbits, the orbit count and the group order.
`Hex.Graph.autos` mirrors it uncoloured, and
`Hex.GraphIso.Mathlib.autos` decodes the generators into
`Colored.Iso G G` values on the Mathlib side.

Two theorems, both on the coloured, uncoloured and Mathlib surfaces:

- `autos_isIso`: every returned generator is an automorphism.
- `autos_sameOrbit`: vertices sharing an orbit representative are
  carried onto each other by an automorphism.

Membership is the checker's, not the producer's. `autom?` rebuilds each
recorded array as a `Perm n` and runs the same `checkIso` the
isomorphism surface runs, so the theorem does not depend on any of the
deep run invariants (`GenTraceOk` and the domination induction are not
cited at all). Orbit soundness comes from `Nauty.orbjoin_orbConn` plus
a short induction turning a `WordConn` word into a composite `Perm`.

`Aut.order` is the orbit-stabilizer chain: find a vertex in a
non-singleton orbit, individualize it (a vertex alone in its cell is
fixed by every colour-preserving automorphism, so the search on the
individualized colouring computes the stabilizer), recurse, multiply
the orbit lengths. One traversal per base point. It is the true order
exactly when every level's orbit array is the true orbit partition,
and a lower bound otherwise; it is not the order of the group
generated by the top-level list either, since the stabilizer factors
come from separate runs. The prose everywhere says so.

## What did not land, and why

The completeness half of the contract, that the returned generators
generate the whole automorphism group, is not proved. It is the
counting argument the issue describes and it is a programme, not a
session. Everything that depends on it is therefore also deferred:

- `numOrbits` and `order` ship as conformance-pinned observables, in
  the same standing as the search counters, and the SPEC says so.
- The tactic. Its interesting goal forms are a stated group-order fact
  and the Mathlib statement about `Fintype.card (G ≃g G)`, and both
  *are* the generation theorem. Proving a given permutation is an
  automorphism needs nothing beyond `checkIso`, so a tactic for that
  alone would be a wrapper with no content. The SPEC now settles the
  goal forms and says the tactic follows the theorem.
- The `leanprover/nauty-ffi` lockstep item, which is a different
  repository.

## Conformance is the load-bearing evidence

The C shim now collects nauty's own generator list through
`options.userautomproc`, plus `orbits`, `stats.numorbits` and
`stats.grpsize`. A new `graphisoautos` fixture kind carries the Lean
answers for 205 cases (every uncoloured graph to four vertices, every
graph-and-partition pair to three, the named families, a Latin-square
graph and two Latin-square incidence graphs, and the pseudo-random
corpus).

All 205 agree with nauty exactly: orbit array, orbit count, group
order, generator count, and the generator lists are identical, not
merely subsequence-related. The oracle asks only for the subsequence
relation because nauty suppresses a tie-leaf automorphism that does not
grow the orbit partition while `genTrace` records it unconditionally;
no case on the corpus exercises that difference. Making `genTrace`
match the emission rule exactly would mean editing `processnode`, which
the domination induction and the `SearchOutcome*` files unfold step by
step, so the honest comparison is the cheaper one.

## Review round

A Codex review found no critical or high-severity issues and six worth
fixing, all folded in:

- the fixture serialized the unchecked `Aut.trace`, so a regression that
  made `autom?` reject a generator would have dropped it from
  `(autos G).gens` while the oracle still passed. It now serializes
  `a.gens`; the emitted file is byte-identical, which is independent
  evidence that nothing is dropped on the corpus;
- the group-order comparison used a relative tolerance once nauty's
  `grpsize2` was nonzero, which accepts wrong integers. It now refuses
  that case outright, since past `10 ** 10` nauty's `grpsize1` is no
  longer an exact integer and every corpus case is far below;
- the Mathlib wrappers called the whole `autos`, paying for the
  stabilizer chain to return a generator list. They take `Aut.gens`,
  `Aut.numOrbits` and `Aut.orbits`, with a new `Aut.gens_isIso` stating
  membership directly on the cheap projection;
- the shim read adjacency rows with an unbounded `scanf("%s")` into a
  fixed buffer (pre-existing). The read is width-limited, the row length
  is checked against `n`, and `n` is rejected above the buffer;
- `Aut.orbitSize` took an unrestricted `Nat`, so an out-of-range vertex
  silently reported vertex zero's orbit. It takes a `Fin n`;
- `autos_isomorphic` concluded `Isomorphic G G`, which holds by
  reflexivity without its hypothesis. Removed.

The local docstrings now say "orbit-stabilizer product" where the value
is not known to be the group order, and the nauty chapter no longer says
a discrete reported orbit array means a trivial group.

One CI-only trap: the pinned `leanprover/nauty-ffi` package's fixture
test reads *every* line of `conformance-fixtures/HexGraphIso/graphiso.jsonl`
and requires `canonLab`, `cellSizes` and `canonTri`, without looking at
`kind`. A new record kind in that file therefore has to be a superset of
a `graphiso` record, which `graphisoautos` now is. The alternative, a
second fixture file with its own oracle entry, costs a new emit
executable and a new `ORACLES` row for no extra coverage.

## Key facts for a successor

- `SearchSt.genTrace` is a superset of nauty's emitted generator list:
  code 1 always, code 2 always, where nauty emits code 2 only when
  `orbjoin` reduced the orbit count. The counts still agree because
  `numgenerators` is incremented where nauty increments it.
- `Nauty.OrbSound`, `Nauty.WordConn` and `Nauty.OrbConn` are plain
  `def`s without `@[expose]`, so a consumer needs
  `import all HexGraphIso.Nauty.OrbJoin` to destructure them.
- `autos` computes the group order, which is one traversal per base
  point. `Aut.gens` and `Aut.orbits` are the cheap projections.
- `check_graphiso_sweep_freshness.py` is a required check and any
  `.lean` file added under `HexGraphIso/` trips it; regenerate with
  `scripts/bench/graphiso_cactus_sweep.sh`. On a machine without
  matplotlib, `uv venv` plus `uv pip install matplotlib==3.11.1` and
  running the script with that venv first on `PATH` works.
