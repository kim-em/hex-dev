# hex-padics SPEC

Session type: feature (issue #9323, `spec: fixed-precision p-adic
approximation libraries`).

## Accomplished

Wrote `SPEC/Libraries/hex-padics.md` for `ZpApprox p N` and
`QpApprox p` and their Mathlib companion, registered the pair in
`SPEC/Libraries/README.md` (description lists, implementation
dependencies, DAG section, index), and pointed the `future-work.md`
bullet at the new SPEC.

The decisions the SPEC turns on, recorded here because a reader of the
diff will want them in one place:

- **Semantics is a ball.** Every statement is about the set
  `B(c, m) = {x : v(x - c) ≥ m}`. Operations are enclosures, so the
  specification of `mul` is membership propagation, never "the
  product". Mathlib-free the membership predicate is over `Int` (for
  `ZpApprox`) and `Rat` (for `QpApprox`); the companion upgrades it to
  `ℤ_[p]` and `ℚ_[p]`.
- **Two types, and the asymmetry is load-bearing.** `ZpApprox p N` is
  capped-absolute with the precision in the type, is a commutative
  ring (it is `ZMod (p^N)` arithmetic), and cannot hold a negative
  valuation. `QpApprox p` is capped-relative with runtime precision,
  handles negative valuation, has a distinguished approximate zero,
  and is **not** a ring: distributivity fails, with a worked `p = 5`
  counterexample where the two sides differ by four significant
  digits. Only the inclusion `a*(b+c) ⊆ a*b + a*c` holds.
- **Two conservation laws.** Addition and subtraction conserve
  absolute precision; multiplication and division conserve relative
  precision. Each row of the precision table is derived in the text
  rather than asserted. Inversion preserves relative precision exactly
  and negates the valuation.
- **Powers are the one place the obvious rule is not sharp.**
  `rel (a^k) = min (rel a + v_p k, 2 rel a)`, so squaring at `p = 2`
  *gains* a digit. A square-and-multiply implementation through `mul`
  is sound and throws that away; the SPEC records the binomial
  derivation showing the higher precision is computable and attained.
- **The success condition is about the represented set, never about
  the approximation ring.** This is the exact opposite of the rule
  hex-truncated-series states, and the SPEC says so. `ZpApprox p 0` is
  the one-element ring in which every element is a unit, while its
  ball is all of `ℤ_p` and contains `0`, so `inv?` must be `none`
  there. That is the fixture most likely to catch a real bug.
- **The checked prime is a `Prop` class.** `PrimeBase p`, obtained
  from `CheckedPrimeCert p` or by `decide`, mirroring hex-mod-arith's
  `ZMod64.PrimeModulus`. Indexing the type on a bundled certificate
  was rejected: certificates are not unique as data, so two
  independently certified copies of one prime would give distinct
  types. The instance is required by every value-creating function and
  every theorem mentioning `ℤ_p`, so a caller cannot reach the
  interesting API without it. Primality is load-bearing three times
  (valuation additivity, unit detection, unit-part normalization),
  with `p = 6` counterexamples for the first two.
- **Mathlib correspondence.** A ball of absolute precision `N` is a
  fibre of `PadicInt.toZModPow N`
  (`Mathlib/NumberTheory/Padics/RingHoms.lean:447`), whose kernel is
  `Ideal.span {p^N}` (line 459). The valuation correspondence must use
  `Padic.addValuationDef : ℚ_[p] → WithTop ℤ`
  (`PadicNumbers.lean:1140`), not `Padic.valuation`, which sends `0`
  to `0` and so cannot state the approximate-zero bound. The companion
  needs hex-primality-mathlib because `ℤ_[p]` requires
  `Fact p.Prime`.

## The review round

Self-review and a Codex review together found eight defects in the
first draft, six of them false statements rather than infelicities.
Recorded because each is a mistake the next reader could repeat.

- **The power rule was wrong.** The first draft gave
  `min (r + v_p k) (2r)` from a term-by-term binomial bound. That bound
  is sound and not sharp, because the tail terms are not independent of
  the linear one. At `p = 3`, `r = 1`, `k = 9` it reports two digits
  while `1⁹`, `4⁹` and `7⁹` all agree modulo `27`. The right statement
  is lifting the exponent on `1 + p^r ℤ_p`, giving `r + v_p k`, with
  the `p = 2`, `r = 1` correction. The replacement is a single `powRel`
  definition, since a second theorem guarded by `2 ∣ k` was false at
  `k = 0`.
- **`toRat?` advertised bounds it did not enforce.** Reconstructing the
  scaled value at the caller's bound and multiplying back by `p^v`
  returns a numerator up to `p^v` too large. The bounds have to be
  scaled with the value.
- **`toRatSym?` returns `none` at relative precision one only for
  `p = 2`.** The symmetric bound at `p = 3` is `1`, not `0`.
- **Zero, One and Pow could not be defined without the prime
  instance,** and the theorem signatures were missing it throughout,
  since a class argument on a definition is not generalized into a
  theorem that mentions it. Both are fixed by putting `[PrimeBase p]`
  on the type formers, following `ZMod64 (p : Nat) [ZMod64.Bounds p]`.
  That is available for a `Prop` class precisely because it is not
  available for a bundled certificate.
- **The named executable operations were never declared.** An
  `instance : Mul` gives `Mul.mul` and `*`, not a bare `mul`.
- **The sharper product precision** is `N + min N (min (v x) (v y))`,
  which exceeds `N` when both factors have positive valuation rather
  than either, and multiplication by an approximate zero *shifts* the
  precision by `w` rather than increasing it. At `w < 0` the discarded
  form is unsound and not merely wasteful.
- **`QpApprox` has no `Zero` and no `One` at all**, which is a second
  and independent reason it is not a ring.

## Current frontier

The SPEC is complete and self-consistent. Nothing is implemented; the
issue explicitly scopes implementation out.

## Next step

Phase 1 scaffolding, in the milestone order the SPEC gives:
`PrimeBase` and `PowTable` first, then `ZpApprox` with its
`decide +kernel` test, then the valuation and inversion, then
`QpApprox`.

## Blockers

None. The three prerequisite libraries (hex-arith, hex-modular,
hex-primality) each already have a SPEC, and hex-modular's
`ratRecon?` is the only piece this library consumes that is not yet
implemented.
