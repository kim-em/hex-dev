# Issue #8901 executable-identity diagnosis

## Accomplished

- Claimed #8901 and sanity-checked the proposed replacement at the
  `DensePoly.gcd` executable boundary before changing production code.
- Found a direct `F_5` counterexample showing that reducing the second gcd
  input can change its unnormalised final-remainder representative by a unit.
- Confirmed the drift is reachable in a complete recursive factorization of
  the monic square-free polynomial `[2, 2, 0, 1, 1]`. The current production
  output is `[[4, 2, 1], [1, 2], [3, 3]]`; the retained reduced-witness
  prototype returns `[[4, 2, 1], [4, 3], [2, 2]]`.
- Verified direct guards with `lake build HexConformance`, then built and ran
  `hex_recursive_relift_spike` natively to pin production/current equality and
  the reduced-output difference.
- Posted the concrete counterexample and executable explanation on #8901,
  removed all temporary diagnostics, and unassigned the issue so a corrected
  directive remains claimable.

## Next step

Revise the directive around an executable identity that is actually true.
One candidate is conditional reuse only when the original witness is strictly
larger than the current factor, which avoids the demonstrated equal-degree
unit scaling; that condition still needs a proof against `gcdAux` fuel and
remainder behavior plus fresh measurement. The other route is an explicit
monic-normalization/output-contract change with every exact expectation and
proof updated deliberately.

## Blockers

coefficients required by #8901. At the reachable child `g = [3, 4, 1]`,
`w = [0, 2, 1]`, `c = 3`, the current gcd is `[1, 2]` while the reduced-input
gcd is its unequal associate `[4, 3]`.
