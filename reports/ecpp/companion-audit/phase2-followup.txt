# Review of the uncommitted HexECPPMathlib follow-up

I found no soundness or correctness blocker in the follow-up code. All nine earlier findings and the open earlier-review items are resolved, three of them with small residuals. What remains is two merge-sequencing problems caused by the release edits still in progress, a few low-severity hygiene issues, and documentation and bookkeeping gaps for phases 2, 3, 4 and 7.

The review was read-only and partial in two ways:
- **Nothing was run.** Shell access was blocked for builds and tests, so this is a static review.
- **Build traces aren't proof.** The `.lake` traces show `Elab`, `Tests` and `LintTests` compiling with no warnings, but I couldn't confirm the traces match the current sources. CI is still the real check.

The working tree also changed while I reviewed it: the lakefile, `released.yml` and the sync script picked up edits that aren't staged yet. I treated those as release preparation, not publication.

## New findings, most severe first

1. **Medium, merge sequencing: the factor exemption pins the wrong lakefile blob.**
   - `ecpp-module-aintlib-lakefile.json` pins `current_blob` `bfc9322e`, which is the staged version.
   - The working tree lakefile is now `76f4cb50`: it adds globs to `HexReleaseTests` and `HexFactorizationModules`.
   - hex-factor freshness reads the index, so it fails as soon as that lakefile is staged.
   - **Fix:** regenerate the exemption from the final lakefile, as the last step. Its reason must also mention the `HexFactorizationModules` change, since that library holds `HexBerlekampZassenhaus.All`. The GraphIso rule isn't affected, because those blocks aren't among the graph's build declarations.

2. **Medium, sequencing: the new `released.yml` entry fails CI while `done_through` is 0.**
   - `check_released_manifest.py:181-195` (run at `ci.yml:130`) rejects any entry below `done_through: 7` that has never been published.
   - **Fix:** keep the entry uncommitted until phase 7 is recorded.

3. **Low: the stop-file test usually leaks the escaped helper process.**
   - In `PariProcess.lean:59-63`, the test writes `.stop` and then deletes it microseconds later, because the task has already finished.
   - The helper process checks for the file every 25 ms, so it usually misses it and lives for its full 20 s.
   - **Fix:** have the helper delete `.stop` itself when it exits, and have the test wait for that deletion with a time limit.
   - **Related residual in `stop`:** the `tryWait` after a kill error can throw and hide the kill error. Wrap it in `try … catch _ => pure ()`.

4. **Low: the quadratic `let` cost moved into evaluation.**
   - `evalCertUnsafe` runs `reduce`, which calls `instantiate1` once per `let`.
   - It's bounded by the 131072-node pass, and only the user's own input can trigger it.
   - **Fix:** build the `Cert` directly from the audited `Expr` with the same `DataContext`, skipping `reduce` and `evalExpr`.

5. **Low: the GraphIso AINTLIB rule only rules out two names.**
   - The rule checks only for the `AINTLIB` and `HasseWeil` prefixes, but AINTLIB's `lakefile.toml` declares 12 libraries (`Common`, `FltRegular`, `LeanModularForms`, …).
   - It can't trigger today, because the cactus import closure doesn't use Mathlib.
   - **Fix:** require the closure to contain no `Mathlib` prefix, since every AINTLIB library imports Mathlib.
   - **Docs:** `SPEC/benchmarking.md` §Checked rules doesn't describe the graph build-declaration rules (the HexBasic flag, Tau Ceti, AINTLIB). This gap predates the PR; the new rule widens it.

6. **Low / nit:**
   - **Duplicate Lake ownership.** In the pending lakefile, `HexECPPMathlib.Tests` is claimed by both `HexECPPMathlibTests` (`lakefile.lean:400`) and `HexReleaseTests` (`:1248`). Native and Pari are claimed by both the `HexECPPMathlib` roots (`:389`) and `HexFactorizationModules` (`:1341`). Lake gives each module to the last match. That's harmless while none of these libraries set options, but it's confusing. Keep one registration.
   - **Weak test.** The new First/Second `sameName` test would also have passed before the N3 fix. The cross-module case (private `p.Certs` in `Main` vs private `p` in `Certs.Main`) is still untested.
   - **SPEC wording.** SPEC lines 133-135 say cleanup always reaps the child. They should mention the kill-failure exception and say outright that generation is POSIX-only, as the README already does.
