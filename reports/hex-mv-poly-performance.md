`bench/HexMvPoly/Bench.lean`. Inputs come from the shared deterministic

The native comparator adapters are reproducible with
`scripts/bench/setup_hex_mv_poly_comparators.py`. The first adapter exercises
CompPoly's actual `CMvPolynomial`; the second exercises the same canonical
sorted-list adapter as the proof probes. Both import the shared corpus. The
five checked-in plots are regenerated by:

```sh
for family in sparse-addition sparse-multiplication cancellation-arithmetic structural-collisions sum-of-squares-arithmetic
do
  python3 scripts/plots/hex-mv-poly-comparator.py --family "$family"
done
```

Reusable container machinery is isolated in `HexBasic/ExtTreeMap.lean`.
In particular, `Std.ExtTreeMap.foldl₂` is a generic ordered joint traversal
and `mergeWith?` is a generic deletion-capable merge. `HexMvPoly` adds only
monomial and coefficient policy. The profiles below identify a linear
deletion-capable tree merge/builder as a plausible future extension of that
same reusable file; it should not be implemented as an `MvPoly`-specific
operation.

## Comparator Ratios

The two named informational tools are **CompPoly CMvPolynomial** and
**Mathlib MvSparsePoly**. Times below are per-call medians in milliseconds.
The ratio is `Hex time / comparator time`: values above 1 mean the comparator
is faster. These are in-process Lean executables, so process-call overhead is
zero rather than subtracted.

CompPoly was pinned at
`f4c59f9e6a00b4e73f3e43ca362480468a508011`. Its export records a dirty
checkout because the reproducible setup changes only the toolchain, Lake
dependency, and two adapter modules. The actual benchmark surface remains
CompPoly's `CMvPolynomial`. Export:
`reports/bench-results/hex-mv-poly-comppoly-7d124888-chungus2.json`
(SHA-256
`f9c0b8d21c1fae2846319dda66c21159c5a4212f9406467d9a01d1f877e9802f`).
All five CompPoly targets are consistent with their derived models: linear
addition and structural traversal, and cubic-logarithmic nested-fold
multiplication, cancellation, and sum-of-squares arithmetic.

The pinned Mathlib revision does not contain `MvSparsePoly`; the referenced
upstream PR series has not landed. Therefore the native and kernel
measurements use a canonical sorted-list proxy with linear addition and
balanced translated-row multiplication. It implements the specified
representation shape, but these results must not be quoted as measurements of
the unavailable upstream implementation. Export:
`reports/bench-results/hex-mv-poly-sorted-proxy-7d124888-chungus2.json`
(SHA-256
`0bae8572ab05c469a2677fc76eb4d585ce727f10098b2feeab6731ec227b5142`).

## Concerns

No unresolved Phase-4 concern remains.

The `Mathlib MvSparsePoly` native curve is explicitly a sorted-list proxy
because the upstream representation is unavailable at the pinned revision.
This is a measurement limitation, not an open Hex implementation defect: the
representation decision is governed by the release-quality kernel sweep and
retains one ExtTreeMap representation. The native addition profile records a
promising future optimization—an efficient deletion-capable joint tree merge
and linear builder—but the current implementation meets its declared model,
and any such primitive belongs in the reusable `HexBasic/ExtTreeMap.lean`
upstream-candidate layer.
