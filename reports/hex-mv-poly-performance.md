# HexMvPoly Performance Report

## Bench Targets

The Mathlib-free compiled suite is registered in
`bench/HexMvPoly/Bench.lean`. Inputs come from the shared deterministic
corpus in `bench/HexMvPolyBench/Corpus.lean`; no random seed is involved.

|---|---|---|
| `runSparseAdditionLex` | `sparse-addition` | `n * log₂ (n + 1)` |
| `runSparseAdditionGrlex` | `sparse-addition` | `n * log₂ (n + 1)` |
| `runSparseAdditionGrevlex` | `sparse-addition` | `n * log₂ (n + 1)` |
| `runSparseMultiplicationLow` | `sparse-multiplication` | `n² * log₂ (n² + 1)` |
| `runSparseMultiplicationHigh` | `sparse-multiplication` | `n² * log₂ (n + 1)` |
| `runCancellationInt` | `cancellation-arithmetic` | `n² * log₂ (n² + 1)` |
| `runCancellationRat` | `cancellation-arithmetic` | `n² * log₂ (n² + 1)` |

| `runSubstCollisions` | `structural-collisions` | `n * log₂ (n + 1)` |
| `runSumOfSquaresArithmetic` | `sum-of-squares-arithmetic` | `n² * log₂ (n² + 1)` |

The native comparator adapters are reproducible with
`scripts/bench/setup_hex_mv_poly_comparators.py`. The first adapter exercises
CompPoly's actual `CMvPolynomial`; the second exercises the canonical
sorted-list adapter used by the proof probes. Both import the shared corpus.
The five checked-in plots are regenerated by:

```sh
for family in sparse-addition sparse-multiplication cancellation-arithmetic structural-collisions sum-of-squares-arithmetic
do
  python3 scripts/plots/hex-mv-poly-comparator.py --family "$family"
done
```

Reusable container machinery is isolated in `HexBasic/ExtTreeMap.lean`.
`Std.ExtTreeMap.foldl₂` is a generic ordered joint traversal, while
`mergeValue?` and `mergeWith?` are generic deletion-capable merges.
`HexMvPoly` adds only monomial ordering, coefficient arithmetic, and the
zero-deletion policy. A direct tree-cursor implementation of the existing
joint fold, together with a linear ordered-tree builder, would support a
linear deletion-capable merge without materializing lists. Those primitives
belong in that reusable file, not in `MvPoly`.

### Consumer acceptance

The public surface was compiled against both named consumers. The exact
migrations and builds are reproducible with
`scripts/bench/setup_hex_mv_poly_consumers.py`.

- `leanprover/sos` at `4e52845513a5a7f70927c96e094592db1bf124d1`
  was migrated through a compatibility module aliasing its old canonical
  multivariate types to `Hex.MvPoly`. `SOS.Certificate`, `SOS.EqElim`,
  `SOS.Symmetry`, `SOS.Verifier`, and `SOS.Tactic` all built as explicit
  `.olean` targets in a fresh clone. `SOSTest.Examples` also elaborated as an
  explicit `.olean` target, replaying its `by sos`, `by sos?`, and pinned
  `sos_witness` examples through the kernel verifier; the complete acceptance
  build passed all 1,545 jobs. The compatibility module requires the
  consumer's existing lawful Boolean equality where executable coefficient
  operations need it, but introduces no blanket `DecidableEq` or Grind
  instance. Its legacy-shaped `aeval` retains CompPoly's exact
  equality-free implicit-argument order as direct `eval₂`; its `eval₂Hom`
  uses the public direct `HexMvPolyMathlib` implementation. Its
  zero/one/add/mul/pow/C/X/neg/sub compatibility lemmas compile against the
  corresponding `HexMvPolyMathlib.aeval_*` theorems.
- `Verified-zkEVM/CompPoly` at
  `f4c59f9e6a00b4e73f3e43ca362480468a508011` was migrated to the public
  `isEmptyRingEquiv`, `finSuccEquiv`, and dense-polynomial bridges.
  `CompPoly.Univariate.CMvEquiv` and `CompPoly.Bivariate.CMvEquiv` passed all
  1,902 jobs under Lean `4.32.0-rc1` in a fresh clone. The reproducible overlay
  rewrites the consumer's `ofPoly_zero` proof through the public ring
  equivalence because the pinned proof no longer elaborates under this
  toolchain; it does not change the statement or runtime adapter.

The setup script applies these compile-acceptance overlays only in temporary
pinned clones. The machine-readable acceptance record is
`reports/bench-results/hex-mv-poly-consumers-b9ce25d6.json` (SHA-256
`9b8744b96e1a8ff08ef0a0a4dedd54c85c9ac1ad13eba5cf16d58e4adc9da3a7`);
it records clean Hex source commit `b9ce25d6`, the pinned revisions, manifest
and adapter hashes, exact build targets, job counts, and hashed Lake output.

## Comparator Ratios

The two informational comparators are **CompPoly CMvPolynomial** and the
**canonical sorted-list MvSparsePoly proxy** used in place of the unavailable
Mathlib `MvSparsePoly`.
Times below are per-call medians in milliseconds. The ratio is
`Hex time / comparator time`; values above 1 mean the comparator is faster.
These are in-process Lean executables, so no process-call overhead is present.

CompPoly was pinned at
`f4c59f9e6a00b4e73f3e43ca362480468a508011`. Its export records a dirty
checkout because the reproducible setup changes the toolchain, Lake
dependency, and adapter modules. The measured type remains CompPoly's
`CMvPolynomial`. Its storage comparator is fixed vector lexicographic order,
including when the shared family generator requests grlex or grevlex.
Consequently these are matched workload-shape comparisons, but not
comparator-identical measurements for every family. Export:
`reports/bench-results/hex-mv-poly-comppoly-b9ce25d6-chungus2.json`
(SHA-256
`2eff063eef8abfe49666c67e12528a6a03ff6d252107447b8fc095c7790ceccf`).

The pinned Mathlib revision does not contain `MvSparsePoly`, so the second
adapter is a canonical sorted-list proxy with linear addition and balanced
translated-row multiplication. It matches the intended comparator for each
family and implements the specified representation shape, but it is not an
upstream Mathlib measurement. Export:
`reports/bench-results/hex-mv-poly-sorted-proxy-b9ce25d6-chungus2.json`
(SHA-256
`78d7ad7ff205d7990752d65ebf694af3c935aece12854b848d8fcbf93b34cb39`).

Both exports used clean Hex commit
`b9ce25d6`, three outer trials per rung, and consistent verdicts throughout.

## Profile

Profiles were captured from clean commit
`23181fc72b705e4defc38c74e647de8b4655c531` on `chungus2` (AMD EPYC 9455
48-Core Processor, x86-64 Linux 6.12.95), with Lean `4.32.0-rc1`,
lean-bench `0.1.0` at `fa30c2763cf523f3ac8e46dc3a1dad0845a40098`,
lean-bench-samply
`9356baa2f5757ee40320a897bd284914d5bb9f5e`, and samply `0.13.1` at
999 Hz. Inputs are deterministic and use no seed. Raw filtered profiles and
symbol sidecars remain under `/tmp` and are not committed.

The common command form was:

```sh
LEAN_BENCH_SAMPLY_HOME=/tmp/lean-bench-samply.XAz9Og/repo \
  scripts/profile/run_profile.sh ./.lake/build/bin/hexmvpoly_bench \
  BENCH_NAME PARAM 5000000000
```

### `sparse-addition`

`BENCH_NAME=Hex.MvPolyBench.runSparseAdditionLex`, `PARAM=4096`.
Leaf cost was allocation/free 47.36%, Lean runtime/Std 47.44%, own
HexMvPoly code 5.16%, other system 0.04%, and GMP 0%. Inclusive cost was led
by the registered target (99.96%), the tree fold (92.63%), `alter` (89.16%),
`Mono.lex` (64.42%), and tree balancing (11.18%). This is the current generic
`mergeWith?` path: it folds one tree through deletion-capable updates in the
other. No preparation phase is present, and the shape directly motivates the
future direct tree-cursor fold and linear builder in the reusable map layer.

### `sparse-multiplication`

`BENCH_NAME=Hex.MvPolyBench.runSparseMultiplicationLow`, `PARAM=128`.
Leaf cost was Lean runtime/Std 44.92%, allocation/free 40.35%, and own code
14.73%; GMP and other system were 0%. Inclusive cost was led by the registered
target (100%), the `MvPoly.mul` tree fold (97.40%),
`addMonomial`/`alter` (95.29%), `Mono.grlex` (84.19%), and monomial degree
folding (7.45%). This is the registered Gustavson-style accumulation path.

### `cancellation-arithmetic`

`BENCH_NAME=Hex.MvPolyBench.runCancellationRat`, `PARAM=256`.
Leaf cost was Lean runtime/Std 41.46%, allocation/free 37.07%, own code
14.61%, GMP 6.84%, and other system 0.02%. Inclusive cost was led by the
registered target (98.16%), the `MvPoly.mul` tree fold (97.15%),
`addMonomial`/`alter` (88.49%), `Mono.grevlex` (67.09%), and `Mono.revlex`
(15.27%). GMP appears as expected for rational coefficient arithmetic; the
dominant work remains the registered multiplication and cancellation path.

### `structural-collisions`

`BENCH_NAME=Hex.MvPolyBench.runSubstCollisions`, `PARAM=1024`.
Leaf cost was Lean runtime/Std 38.07%, own code 36.89%, and allocation/free
25.04%; GMP and other system were 0%. Inclusive cost was led by the registered
target and `MvPoly.bind`/`subst` tree fold (99.98%), `Mono.prod` (82.19%),
the inner `MvPoly.mul` fold (63.63%), and `Mono.powBySq` (54.72%). These are
the expected substitution stages and all belong to the registered structural
target.

## Concerns

[Issue #9805](https://github.com/kim-em/hex-dev/issues/9805) tracks the
unresolved representation experiment described below.

The implementation milestone is complete. The representation experiment is
not a positive performance result: all five terminal comparisons remain
statistically unresolved. Under the predeclared gate, zero families pass.

The Mathlib-native curve is explicitly a sorted-list proxy because
`MvSparsePoly` is unavailable at the pinned revision, and CompPoly's fixed
lexicographic comparator prevents exact comparator matching on every family.
These are disclosed measurement limitations, not Hex implementation defects.

The release-quality kernel gate does not justify a second representation.
Within the single `ExtTreeMap` implementation, the addition profile identifies
a promising optimization: a direct tree-cursor version of the existing
ordered joint fold plus a linear tree builder. Such primitives belong in the
reusable, Std-only `HexBasic/ExtTreeMap.lean` upstream-candidate layer.
Coefficient combination and removal of zero coefficients remain `HexMvPoly`
policy.
